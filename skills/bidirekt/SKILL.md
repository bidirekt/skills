# Bidirekt contracts

Write and update the service's Bidirekt contract files from its code, check them against the broker, and fix them from a deploy-check report.

https://bidirekt.com/llms.txt is the only reference. The rules of the contract file, the CLI commands with their flags and messages, the report shape and what each break line means all come from there; this file gives only the steps. In every step:

- The contract describes what the code does. Change only the service's own contract files, never the code (except the SDK annotations, below), and never change a contract only to make a check pass. A GraphQL service's schema files (`.graphql`, `.graphqls`, `.gql`) are part of its code: never write, regenerate, edit or delete them.
- Run only the CLI commands that read: the local validation (it checks the files and, with the participant and an environment, compares them with the counterparts deployed there, storing nothing), the participant list and the environment list. With the SDK, also the SDK command that generates the contract, which writes only `contracts/generated.yaml`.
- Run each CLI command alone, as the whole command line: nothing chained or appended to it (`;`, `&&`, `|`, `echo $?`). A `BIDIREKT_PROFILE=<name>` prefix is part of the command. The shell already reports the exit status, and the report's first line says the result.
- Never store a contract version in the broker, never run the deploy check (it asks whether a stored version can be deployed and records the answer in the broker), never record a deployment, never create a participant or an environment, never rename a participant. The engineer runs those.

## With an SDK

The project uses an SDK when:

- TypeScript SDK: its `package.json` lists `@bidirekt/typescript-sdk` or `@bidirekt/typescript-sdk-cli`, or its `contracts/generated.yaml` starts with `# Generated by @bidirekt/typescript-sdk. Do not edit.`
- PHP SDK: its `composer.json` lists `bidirekt/php-sdk`, or its `contracts/generated.yaml` starts with `# Generated by bidirekt/php-sdk. Do not edit.`
- Go SDK: its `go.mod` requires `github.com/bidirekt/go-sdk`, or its `contracts/generated.yaml` starts with `# Generated by github.com/bidirekt/go-sdk. Do not edit.`

Then the contract lives in the code as annotations, and `contracts/generated.yaml` is the service's only contract file, beside the GraphQL schema files of a subgraph (step 4). In every step:

- Read also that SDK's page that llms.txt links to, and the README the page links to for the full reference (`https://raw.githubusercontent.com/bidirekt/typescript-sdk/main/README.md`, `https://raw.githubusercontent.com/bidirekt/php-sdk/main/README.md` or `https://raw.githubusercontent.com/bidirekt/go-sdk/main/README.md`), as raw text, the way step 1 reads llms.txt: the annotation rules and the command that generates the contract come from there. If either cannot be read, stop as in step 1.
- Write the contract as annotations: add and fix the provider, consumer and field annotations, and create each schema in the form the project already uses: decorators or tags with the TypeScript SDK, attributes or docblock tags with the PHP SDK. With the Go SDK, the annotations are `bidirekt.*` declarations and `bidirekt` struct tags. Only the TypeScript SDK annotates GraphQL: the calls the service makes and the graph of a subgraph. With the PHP or Go SDK, a GraphQL call is something the contract cannot express (step 4). Change nothing else in the code.
- Never edit `contracts/generated.yaml`. After every change to the annotations, generate it, then run the local validation on it. For a subgraph, run it on `contracts/generated.yaml` together with the GraphQL schema files: alone, it fails with `graph "<name>" without a GraphQL schema`.
- Fix the breaks of a deploy-check report in the annotations (step 8), then generate again.
- When the service adopts the SDK and has hand-written contract files, move the whole contract into annotations, generate, check that the new file declares everything the old files did, and delete the old YAML files. A subgraph's GraphQL schema files stay, and are passed with `contracts/generated.yaml` from then on. When the SDK cannot express part of the old files (GraphQL with the PHP or Go SDK), stop before deleting anything and tell the engineer.

Without the SDK, skip this section.

## 1. Read llms.txt

Before anything else, fetch https://bidirekt.com/llms.txt and read the whole file as raw text. Run exactly `curl -sSfL https://bidirekt.com/llms.txt`, with no other flag and no command chained to it: `-f` already fails on any answer that is not 2xx. Use a web fetch only when there is no shell; if it returns a summary instead of the file, treat the reference as unreadable. Follow its rules, commands and messages in every step.

If the fetch fails, the answer is not 200, or the content is not the Bidirekt reference (an HTML page, a parked-domain page, an error page): stop, tell the engineer that the reference at https://bidirekt.com/llms.txt could not be read, and write nothing. Never write a contract from memory or from another copy, and never guess the grammar.

## 2. Check the CLI and the broker

Before writing anything, run the participant list. The call needs the CLI binary that llms.txt names, on the PATH, and a configured broker:

- The binary is not found: stop, and show the commands from the `## Setup` section of llms.txt that install the CLI and point it at a broker.
- The CLI answers that no broker is configured (llms.txt documents the message):
  - it also names one profile of the config file: use it, with `BIDIREKT_PROFILE=<name>` or `--profile <name>` on every later command, and tell the engineer which profile you used;
  - it names several: ask the engineer which one, and wait;
  - it names none: stop, and show the commands from `## Setup` that point the CLI at a broker.
- Any other error: stop, and show it to the engineer.

Never install the CLI or point it at a broker yourself: the engineer does that.

## 3. Settle the names

Read the code, then settle every name before writing anything. When a name needs the engineer, ask and wait.

- The service's own participant: take it from where the project already passes it to the CLI (a CI workflow or a script); otherwise ask the engineer. Never save it anywhere.
- The environment for the local validation: from the same places, or ask. Check it against the environment list. If a named environment is not there, run nothing with it: show the similar names from the list and ask. When nobody named an environment and either the environment list is empty or the engineer says there is none yet, run the local validation without the participant and the environment.
- Each provider the service calls: deduce its participant name from the code (the client's name, or an environment variable such as `PETSTORE_API_URL` → `petstore_api`) and check it against the participant list. If it is not there, do not write it: show the similar names (`petstore_apl` → `petstore_api`?) and ask. If the engineer confirms a new provider that is not in the broker yet, write it and warn that the deploy check fails until that provider stores its contract in the broker. The breaks that come only from that provider are then expected: keep the calls and report the breaks.
- A GraphQL call goes to a participant that serves the GraphQL schema itself, or to a federated graph, under the graph's name (`PETSTORE_GRAPH_URL` → `petstore_graph`). A graph name is a valid provider name but is not in the participant list: never treat it as a missing participant. Take it from the `provides.graphql.graph` of a subgraph whose files are within reach, or ask the engineer.

## 4. Write the contracts from the code

Whatever the language, find in the code:

- the resources the service serves, of the kinds llms.txt documents → `provides`;
- a GraphQL schema the service serves: its own schema files are its contract, passed to the CLI as they are. When the schema links Apollo Federation, the service is a subgraph: declare its graph in `provides.graphql.graph` of a YAML file, or with the SDK's graph annotation. When the project has no schema file (the schema is built in code), write none: tell the engineer the CLI needs the schema as a file;
- the calls it makes to other services → `consumes`, under each provider's name from step 3. A GraphQL call is `consumes.<provider or graph>.graphql.query` (or `mutation`), keyed by the root field the operation calls, with `arguments`, the schema of the arguments the code sends, and `returns`, the shape the code reads from the answer;
- the types of the bodies it serves, reads and sends → `schemas`.

Write them as llms.txt says. When the code does something llms.txt has no way to express, leave it out and tell the engineer; never invent syntax.

Write `optional` and `nullable` from what the code does, following the rule for modeling null and absence in llms.txt, never from the declared type. With the SDK, the declared type is where each field starts, and the annotation's `type`, `optional` and `nullable` options apply this rule where the code differs from it. When the type says nullable or optional but no code path produces `null` or leaves the key out, write neither and tell the engineer the type is wider than the code. When the code does not let you know, ask.

Folder: `contracts/`, or the folder the project already uses for contracts (for example, where the files its CI passes to the CLI live). A GraphQL provider's schema files stay where the code keeps them, and are passed by their paths. A folder passed to the CLI sends its `.graphql`, `.graphqls` and `.gql` files too, so the client's GraphQL operations (the queries and fragments the code sends) never go in the contracts folder: the broker refuses them with `holds client operations; publish expects the GraphQL schema`.

How to organize the files (recommendations, not rules):

- modular project: one file per module;
- not modular, with few resources: one file;
- more than 50 resources, or more than 50 schemas: more files, such as `provides.yaml` and `consumes.yaml`;
- monolith or microservice changes nothing: the context is the current service;
- the project already has an organization: follow it.

With more than one file, follow the rules llms.txt gives for several files.

## 5. Update an existing contract

When the contract files already exist, edit them in place; never regenerate a file. With the SDK, edit the annotations in place; `contracts/generated.yaml` is always generated again.

- Change only what the code changed. Keep the comments, the order, the formatting and every `description`.
- Remove a resource or a property only when the code stopped using it, and list every removal in the final answer: on the provider side, a removal can become a break for a consumer.

## 6. Check the changes

1. Run the participant list and check every provider name under `consumes` against it, as in step 3 (a graph name is not in it).
2. Run the local validation on the files, with the service's GraphQL schema files when it serves one: it checks them and, with the participant and an environment, compares them with what is deployed there. Pass the participant and the environment settled in step 3, or neither when there is no environment.
3. Fix the contract from what they answer, as llms.txt explains, deciding each break line as in step 8, and run both again until the validation passes.

Stop looping when the only fix left contradicts the code: tell the engineer that either the code changes or the counterpart is asked, and write the request as in step 8. Stop too when the only breaks left are the expected ones of a new provider (step 3), and report them.

If the local validation answers that the service's own participant does not exist, stop and tell the engineer, with the similar names from the participant list: creating it is the engineer's decision.

## 7. Finish

List the files written or changed, every removal, every warning and every request for a counterpart. When the local validation ran without an environment, say that it checked only the files, and that the comparison with what is deployed was not done. When a contract file changed, end the answer with the next command to run: the command from llms.txt that stores the contract in the broker, with the participant and the files (the GraphQL schema files too, when the service serves one), and the version as a placeholder (or the one the project's CI uses). With the SDK, list the code files changed, and put the command that generates the contract before the one that stores it.

## 8. Fix the contract from a deploy-check report

The engineer pastes the report in the conversation, or points to a file that has it (a CI log). Do steps 1 and 2, and settle the service's own participant and the environment as in step 3 (the report names the environment). Find the report by the shape llms.txt documents, and read each break line with the section of llms.txt that explains each break line and its fix.

For each break line, find the spot it names (counterpart, endpoint, method, request or response status, property path) in the service's contract and in its code, and decide whose change fixes it. A GraphQL break names the operation and the field in both schemas: `Query.pets(limit:) — petstore_api requires it, but petstore_web doesn't send it` ends with `· query pets arguments (argument "limit")`, and `Pet.reviews — petstore_reviews (via petstore_graph) provides it as String!, but petstore_web reads [String!]!` with `· query pet returns at "$.reviews" (petstore_web: Pet.reviews)`. `(via <graph>)` names the subgraph that provides the field through the graph: a fix on the provider's side is that subgraph's. A line that says the graph can't be built, or that a subgraph makes it fail to compose, points to `/graphs/<graph>`: the subgraphs' schemas do not compose, no contract fixes it, and it goes to the engineer as it is.

- The service's, when its contract does not describe what its code does there (for example, the code does not read that property, or works without it): change the contract to match the code, the way llms.txt gives for that line, and go through step 6 again. When the spot is in the service's own GraphQL schema, the schema is the code: change nothing, and tell the engineer.
- The counterpart's, when the contract already describes the code: change nothing of the counterpart's, even when its files are within reach, and write the request for the counterpart: what to change, where (endpoint, method, request or response status, property path; for GraphQL, the operation, `arguments` or `returns`, and the field) and why (the break line). If a change in the service's code would fix it instead, say so: that choice is the engineer's.

Then finish as in step 7.
